# DETERMA — Canonical Strategy for Architecture Generation Systems

Status: Canonical Strategic Document  
Scope: Product Direction, Category Discipline, AIL Positioning  
Authority Level: Binding Strategic Guidance  
Purpose: Prevent category dilution and preserve DETERMA as a deterministic governance system rather than a generation platform.

---

# 1. Canonical Strategic Decision

DETERMA MUST NOT become:

- an AI architecture generator
- an autonomous software factory
- a planning IDE
- a generalized architecture cognition platform
- an AI SDLC suite
- a semantic graph intelligence platform

DETERMA MUST become:

> The deterministic governance layer for autonomous system evolution.

This is the canonical boundary.

Generation systems may evolve architectures.

DETERMA governs whether those evolutions remain legitimate.

---

# 2. Canonical Market Thesis

The software market is evolving through four stages:

| Stage | Capability | Primary Failure |
|---|---|---|
| Stage 1 | AI code generation | bad code |
| Stage 2 | AI architecture synthesis | architecture drift |
| Stage 3 | autonomous mutation systems | illegitimate mutation |
| Stage 4 | recursive autonomous evolution | constitutional collapse |

DomForge-class systems represent Stage 2.

DETERMA targets Stage 3–4.

Therefore:

> Architecture generation systems increase the necessity of DETERMA.

They are not the category DETERMA should enter.

# 10. Canonical Mutation Legitimacy Model

Every architecture mutation must pass:

## Step 1 — Proposal

Mutation proposed externally.

Examples:

- service split
- API modification
- dependency addition
- ownership transfer
- topology modification

---

## Step 2 — Constitutional Classification

DETERMA classifies mutation type:

| Mutation Type | Classification |
|---|---|
| logging update | operational |
| retry policy tuning | policy |
| service boundary change | constitutional |
| ownership transfer | constitutional |
| authority rule modification | constitutional |

---

## Step 3 — Architecture Witness

DETERMA computes:

- topology hash
- dependency graph hash
- OpenAPI hash
- ownership integrity hash

---

## Step 4 — Invariant Validation

AIL validates:

- forbidden dependencies
- API drift
- ownership violations
- unauthorized coupling
- authority expansion

---

## Step 5 — Human Approval

Constitutional mutations require:

- dual human approval
- invariant impact declaration
- cooling-off enforcement

---

## Step 6 — Capability Release

Execution receives:

- narrow scope
- short TTL
- single-use authorization

---

## Step 7 — Constrained Execution

Executor may mutate only:

- approved files
- approved topology
- approved systems
- approved scope

---

## Step 8 — Verification and Immutable Lineage

DETERMA verifies:

- resulting architecture state
- dependency graph integrity
- API integrity
- actual mutation scope

Then records immutable lineage.
